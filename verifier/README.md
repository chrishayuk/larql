# LARQL contract verifier

**Class: CURRENT.** Measures a VINDEX3 container against a numerical contract. It's what LQL's `VERIFY REPRESENTATION` runs.

It ships with LARQL, but it isn't built from LARQL: it's a separate Python package with no LARQL code in it, so that LARQL can't mark
its own work. [docs/verification/independence.md](../docs/verification/independence.md) says what enforces that, and what doesn't.

**A result is a numerical measurement.** It isn't a formal proof. `Q8_0_T2` measures one container, and isn't a claim about the encoder that produced it. `Q8_0_GEMV_SEQ` and
`Q8_0_GEMV_B1` measure one recorded kernel call, from a witness the engine wrote. `Q8_0_GEMV_B1` is experimental. See the [protocol](../docs/verification/contract-protocol.md#operator-contracts-larql-verify-operator1).

**A result doesn't authenticate the verifier.** The code digest in an answer is the program's report about itself, which helps reproduce a result.
Replacing the program could make a contract appear satisfied without changing the model, so a result must not gate a release on this basis.
[What a release gate would need](../docs/verification/independence.md#the-verifier-is-not-authenticated).

## Results

`Q8_0_T2` requires every element of every Q8_0 tensor to be within the T2 reconstruction bound of its source value. On two containers of
Qwen3-0.6B at `c1899de2`:

| Container | Encoded with LARQL | Result | Elements over T2 |
|---|---|---|---:|
| Original | `2536bb79` | `violated` | 57,634 |
| Corrected | `a23b37b8` | `satisfied` | 0 |

## Install

From `verifier/`, with Python 3.12 and [uv](https://docs.astral.sh/uv/). It doesn't need `torch`, or a built LARQL.

```sh
uv venv --python 3.12 .venv
VIRTUAL_ENV=$PWD/.venv uv pip sync --require-hashes requirements.lock
VIRTUAL_ENV=$PWD/.venv uv pip install --no-deps .
```

## Use

```sh
.venv/bin/larql-verifier contract --contract Q8_0_T2 --container <dir> --source <checkpoint dir>
```

The [protocol](../docs/verification/contract-protocol.md) specifies the invocation and the answer, how LQL finds a verifier, and how to
write a different one.

### `EXECUTION_RESIDENCY_V1`: what a run loaded against the container it loaded from

```sh
.venv/bin/larql-verifier residency --contract EXECUTION_RESIDENCY_V1 --record <residency record> --container <container>
```

Implements [execution-residency-v1.md](../docs/verification/execution-residency-v1.md). The engine writes a residency
record of what each matrix operand was made resident as. This re-derives every resident representation from the
container's stored bytes (the loader's 64-element-block Q8, exact widening to binary32, or the stored bytes kept) and
re-decides every choice from the recorded policy and cache size, as two separate verdicts: **derivation** and
**selection**. A record that omits an operand, names a rule this contract does not derive, or was made from another
container is never satisfied. It judges the engine's own account of what it loaded; it does not show that a kernel
consumed those bytes.

### `WEIGHT_PATCHES_V4`: a compiled structured edit against its base

```sh
.venv/bin/larql-verifier ledger --contract WEIGHT_PATCHES_V4 --base <base container> --container <compiled container>
```

Implements §7 of [weight-patches-v4.md](../docs/verification/weight-patches-v4.md). It recomputes every edited tensor from the base's
weights and the ops the compiled container's `weight-patches/v4` ledger records, with its own implementation of the frozen numerics
(`contracts/vlp_numerics.py`, `conformance/vlp-numerics/v1` and `v2`), and compares **every** element. The ledger's hashes and counts
are only checked against that, never used as expected values. The answer (`larql-verify-ledger/1`) carries two verdicts, kept apart:
`numerical_satisfaction` (§7 step 3) and `ledger_integrity` / `provenance` (one half: §7 steps 1, 2, 4, 5), with each finding tagged by
its half under `verdicts`. `status` is `satisfied` only when both are. What the engine says about itself is under `engine_reported`; the
`verifier` block is this program only.

It recomputes every op's §3a digest. It doesn't establish the operands' `origin`, judge `candidate.json` (regenerated by every compile),
or check the content of re-derived (quantised) representations, whose digests it chains to the compiled canonical payload without
re-quantising. The answer is specified in the [protocol](../docs/verification/contract-protocol.md#ledger-contracts-larql-verify-ledger1).

A segment the compile neither edited nor re-derived is judged as a whole file: byte-identical to the base's file satisfies §7 step 4
for every tensor in it, but its tensor table is not parsed, so its internal structure is **not** validated, and the answer says so
(`untouched segments judged as whole files (byte-identical; internal structure not validated)`). Edited and re-derived segments are
parsed, and a duplicate tensor name there is refused. (The real Gemma 3 4B base lists `mm_soft_emb_norm.weight` twice in its
untouched `vision.perception_adapter` segment; that is an encoder defect, tracked separately.)

**Independence and its limits.** The numerics here are written from the frozen specifications and the v4 contract alone: nothing in
this package calls, links or ports the Rust engine, and it must stay that way. But the contract was not unchanged while this was
built: three revisions of `weight-patches-v4.md` on #810 (e3ca8f69 bounds stated inline and inclusive; 2d15ff54 the op digest, element
targets, `candidate.json` and the verdict halves; b0176188 untouched segments as whole files) answer gaps that building it found. The
tests therefore establish **conformance** to the final contract and **mutation sensitivity** (deliberate corruption is rejected, in
the half it belongs to). They are not an independent replication against a contract frozen beforehand; that needs a fresh
implementer or reviewer working from the frozen version.

The four containers in `conformance/weight_patches_v4/` were compiled by the engine (`make_fixtures.py`, recorded in
`provenance.json`); they are inputs to judge, not oracles. Every expected value is recomputed here from the base and the ops.

## Reproduce

```sh
./reproduce.sh
```

It downloads the checkpoint from Hugging Face, builds LARQL at each commit in a separate worktree, encodes a container with it, measures it,
and compares the status, the violation count, the report digest and the Q8_0 segment's digest with `expected/qwen3-0.6b.json`.

It then runs the corrected container through LARQL with the capture on, checks the recorded calls and logits against the expected digests, and asks
`VERIFY OPERATOR` about three operators under both contracts. Last, it builds two faulty kernels in a temporary worktree and checks they're judged as expected: summing
blocks in reverse must fail `Q8_0_GEMV_SEQ` and pass `Q8_0_GEMV_B1`, and reading codes as unsigned must fail both.

For each checked operator it also compares the verifier's worst error as a fraction of the B1 bound with the expected value.

It needs git, curl, a Rust toolchain, whatever LARQL needs to build and about 12 GB of disk.

Every engine step writes a log under the work directory (`build.log`, `encode.log`, `represent.log`, `exec.log`, and one answer
file per `VERIFY OPERATOR` statement). Whatever stops the run, it ends with `Reproduced.` or `NOT reproduced.`, says which step
failed and where its log is, and removes its temporary worktree. A fault that can no longer be injected, or a capture the engine
refuses, is reported as not checked, never as a pass.

**What the expected values are.** The digests, the record and call counts and the worst-error ratios in
`expected/qwen3-0.6b.json` are regression pins: they were recorded from one run of the pinned LARQL commits, not derived
independently. They show that a run reproduces that one, not that its numbers are right. Two expectations are derived in advance:
summing blocks in reverse is a reassociation, so it breaks `Q8_0_GEMV_SEQ` but stays within `Q8_0_GEMV_B1`'s bound; and reading
signed codes as unsigned gives wrong values, which both contracts reject.

**Where it has been run:** macOS on Apple silicon only. Encoding on other platforms hasn't been compared.

A container's overall digest isn't in the expected results, because `candidate.json` records the path of the encoder's input. So it differs
between machines even when the weights are identical.

## Tests

```sh
.venv/bin/python -I -m unittest discover -s tests
```

The tests are synthetic, apart from one that runs if you set `LCV_SOURCE` to a real checkpoint directory. `LCV_BENCH=1` also times
`WEIGHT_PATCHES_V4`'s arithmetic on a Gemma-3-4B-sized rank-one edit.

## What it does and doesn't establish

- **T2** is derived from ggml's reference encoder: `|x − q·d₁₆| ≤ d₁₆·(½ + 2⁻¹² + 2⁻¹⁶ + 127·2⁻¹¹) + 127·2⁻²⁵`, for an element `x` in a block
  with stored scale `d₁₆` and code `q`. It has been checked empirically, not formally proved.
- **`satisfied`** means no element of those tensors exceeded the bound in that container. It says nothing about any other container, or about
  how a model behaves when run.
- **`could_not_evaluate`** is never a pass. It's what you get for an unknown contract, an unpinned source, a container with no Q8_0 tensors, or
  anything T2 makes no statement about.
