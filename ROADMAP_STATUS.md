## Recently shipped (delta since last update)

- **Memory-bandwidth roofline measured; a 3.3× spin-pool regression found and fixed on every non-bench path (2026-07-29).** The whole speed programme was being argued with two numbers that are not the same kind of number: an *achieved* "larql extracts ~47 GB/s vs llama.cpp ~70" (recorded **before** the spin pool landed +28%) and the SoC **spec sheet**'s 400 GB/s. Achieved-vs-spec is not a roofline, so a new probe ([`crates/larql-compute/examples/membw_probe.rs`](crates/larql-compute/examples/membw_probe.rs)) measures the missing quantity — what the hardware actually delivers, per processor. **CPU cluster 127 GB/s read, saturating at *two* threads; GPU 367 GB/s; SoC spec 400.** The CPU cluster reaches **31%** of the chip's bandwidth and the GPU **92%** — a **2.9× structural advantage no CPU kernel can close**, since it is P-cluster fabric ports. The Metal production kernels already run at 273–314 GB/s (74–85% of attainable), which makes the roofline a much stronger argument for the G-ladder than "CUDA parity" was; the one outlier is `q4k_qkv_proj` at 130.8 (36%). The probe self-checks against C12's issue-rate trap (each arm run DRAM- *and* cache-resident): `read` 11.4× ⇒ genuinely memory-limited, `copy` 1.05× ⇒ reported as a **floor by design**, since stores reach memory in both arms. **The 47 GB/s was stale**: it came from the bench's hand-rolled rayon arm, not the shipping path — a new `bench_mt_production` arm on the real entry point puts that same shape at **98.7 GB/s**, and per-layer shapes at **50–91% of attainable, not 37%**. Consequence: **CPU bandwidth work is essentially finished** (≤~1.6× theoretical headroom), and the bandwidth-bound half belongs on the GPU. **The regression:** `spin_pool::global()` sized itself from `rayon::current_num_threads()`, but `configure_rayon_threads` is called from *exactly one place* — the CLI bench path, which picks 8 on Apple silicon — so `larql run`/`larql serve` inherited `available_parallelism()` = 16 = 12 P + 4 E. The pool partitions statically, so an efficiency core takes a performance core's share and the barrier waits on the slowest participant (rayon work-steals, hence pool-specific). Measured 16 participants **33 GiB/s** vs 12 → 124 and 8 → 126.7; **end-to-end 10.6 tok/s vs 37.3 on the 26B**. Fixed by capping the pool at the performance-core count in the **library** (not the CLI, so larql-server and embedders inherit it) — **verified 10.6 → 34.9 tok/s, 3.3× recovered**. Two carry-forwards: the **bench harness was structurally unable to see this** (bench was the only path setting a thread count, so every historical spin-pool number was taken on the one config that avoids the bug), and **criterion's default sampling flattered it** (58.5 GiB/s short-run vs a consistent 33 at `--measurement-time 20`). A first hypothesis — strided chunk ownership defeating the prefetcher — was **wrong and killed by measurement**: contiguous blocks did not close the gap, participant count did; the block change is kept for the prefetch property and pinned by its own test. Also corrects the "at the 400 GB/s GPU ceiling" claim in `larql-compute`'s ROADMAP/CHANGELOG. Writeup [`docs/diagnoses/memory-bandwidth-roofline.md`](docs/diagnoses/memory-bandwidth-roofline.md). **Unchanged by any of this:** arithmetic intensity — bandwidth ceilings are a denominator, and DEC-0's 13.9%-unique-at-B64 (~7.2× grouped-scheduler headroom) remains the only measured un-harvested lever. **Still unpriced:** KV-cache bytes (`CpuKvHandle` holds `Vec<f32>` against llama.cpp's f16 default; C10's context decay was attributed to GQA compute and never tested against the bytes hypothesis).

- **`larql recipe build` — the PREFLIGHT→RELEASE build driver, §7 (2026-07-29).** New `larql-factory::build` module: `run_build` orchestrates FETCH (`larql model pull`) → EXTRACT (`larql extract`) → SLICE (`larql slice`, skipped for the `full` preset) → MANIFEST (recursive byte-size measurement) → VERIFY (`larql verify`, checksum integrity) → PUBLISH (`larql hf publish --private`, one call per output) → RELEASE (`larql hf visibility --public`, only after every output verifies) as subprocess calls into the same `larql` binary, behind a `CommandRunner` trait — `SubprocessRunner` (real, self-invokes via `current_exe()`) for production, a scripted `MockRunner` for tests — so every stage's argument-building and ordering is unit-tested without spawning a process or touching credentials. FETCH scopes `HF_HUB_CACHE` to a per-build directory: `larql_models::resolve_model_path`'s cache lookup doesn't disambiguate by revision (returns the first cached snapshot with safetensors, whatever revision that is), so a shared cache could let EXTRACT silently build from a stale cached commit despite FETCH correctly pulling the pinned one. PUBLISH always uploads `--private`; RELEASE is the only stage that flips a repo public, and only runs after every output has passed VERIFY — §8's "nothing goes public unverified" contract, made real rather than just documented. Repo names are computed via the same `card::naming` logic the card generator's `USE` snippet uses, so a build and its own card can't disagree about where something published. Always returns a `BuildRecord` (`build_id`, `recipe_name`, per-output `{preset, size_bytes, repo, released}`, and a flattened `status` — `"passed"` or `"failed"` + which stage + its message) as JSON, whether the build succeeded or a specific stage failed — matching `dec-bench`'s `--output-file` pattern rather than a bare process exit code. **Scope decided by tracing what actually exists in this codebase, not what the spec assumed**: MIRROR (R2 upload) and REGISTER (chuk-experiments-server) aren't implemented — no S3/R2 client exists anywhere in the workspace, MCP tools aren't callable from compiled Rust, and REGISTER needs a `run_id` only external dispatch (`submit_run_from_experiment`) can create; the spec's own text assumes both are the rig worker's job. `BuildRecord` is the intended hand-off point for an external wrapper to do both, the same way `dec0-loopback.sh` already wraps `dec-bench`'s own JSON output. VERIFY here is checksum integrity only — the numeric reconstruction/logit-match checks §8.1 describes need per-architecture tensor-naming knowledge (mapping "layer N's down_proj" to the right safetensors key per model family) that isn't validatable without real model weights; confirmed neither `larql shannon verify` nor `larql dec-bench drift` do vindex-vs-upstream comparison despite the spec assuming they did. Extended `larql-vindex`'s publish path (`PublishOptions.private`, `create_hf_repo`'s create-repo body) and added a new `set_repo_visibility`/`update_repo_visibility` capability — verified against the real HuggingFace OpenAPI spec (`PUT /api/{repo_type}s/{repo_id}/settings`) rather than guessing the endpoint shape — to make private-then-public two-phase publish possible at all; wired into the CLI as `larql hf publish --private` and a new `larql hf visibility <repo> --public|--private [--repo-type T]`. Wired into `larql recipe build <FILE> [--scratch-dir DIR]`, printing the `BuildRecord` and exiting non-zero on failure. Every new source file at or above the 90% coverage floor (192 tests in `larql-factory`'s own suite).
- **Windows CI unbroken — `larql-vindex` green for the first time since 2026-06-19 (2026-07-25).** The dense-only/client-slice gate buffer mapped zero bytes then called `make_read_only()`. memmap2 clamps the *underlying* Windows mapping to one byte but records the requested length of 0, so `virtual_protect` reached `VirtualProtect(ptr, 0, PAGE_READONLY, …)` — `ERROR_INVALID_PARAMETER` (os error 87). | Area | Decision |
|---|---|
| Single P0 | The **DEC funnel** is the active programme. Within it, DEC-1A is the central experiment (its fitted latency model is what DEC-2 and DEC-CV consume); the G-ladder is the long pole and runs in parallel. V1–V4 is closed — see the resolved section above. |

The serving path logs its kernel class at startup; wire-format fallbacks are recorded in `served_wire`/`served_wire_out`. | MoE-first | Functionality emphasis stays MoE (80% tier) over dense (15%): CPU MoE forward + hash-routed FFN + disk-resident expert paging are the crown jewels. Dense-31B substrate-primary (ADR-019) is for velocity, not the destination. |

| Multi-machine MoE | Stays P2 unless a specific experiment or frontier-scale release re-promotes it. |
