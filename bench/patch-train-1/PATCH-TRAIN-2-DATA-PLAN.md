# PATCH-TRAIN-2 data generation plan (DRAFT r2, 2026-11-14; direction approved, generator not yet reviewed; nothing generated)

Companion to `PATCH-TRAIN-2.md` r3 §5.1. **No generator code is written or run and no example exists until this plan is reviewed.**
Branch `research/structured-real-1`. The frozen v2 numerics contract is untouched.

## 1. Why a new dataset

`tasks_discovery.json` and `tasks.json` are both treated as DISCOVERY data. Discovery observed many of their entities as leakage
comparisons and those observations informed the layer, address and cap choices. A clean development/confirmation split therefore
needs entities that no discovery run has ever seen, generated by rules that are fixed first.

## 2. What is fixed before generation (all committed together, before the generator is run)

| Item | Rule |
|---|---|
| Generator | `competence/generate_patch_train_2.py`, a new file; `build_tasks.py` is not modified |
| Relation | "capital of a fictional country" only (task A). Train template `The capital of {e} is`; 3 held-out templates as in discovery (templates are not entities; the reuse is disclosed) |
| Answer vocabulary | the same 12 single-token city answers (verified single-token by the tokenizer, as in discovery) |
| Name process | the same syllable process as `build_tasks.py` (2-3 syllables from the same 16, capitalised, suffix `ia`), so name statistics match discovery |
| Seeds | CAL `20261121`, CONF `20261122`, RET `20261123` (approved 2026-11-14). Committed in `competence/patch_train_2_seeds.json` before any real generation; never changed |
| Splits | CAL: 4 pairs = 8 entities. CONF: 12 pairs = 24 entities. RET: 24 entities (fixed retention pool for D). Splits are entity-disjoint from each other and from the discovery files |
| Exclusion | no generated name may equal any entity name in `tasks_discovery.json` or `tasks.json` (either task), any real-fact country, or any name in another split. The sha256 of the sorted exclusion list is written into each output as provenance |
| Format acceptance | a name is accepted only if `" " + name` tokenises (Gemma 3 tokenizer, `add_special_tokens=False`) to **2 to 6 tokens**, the range spanned by every discovery name (measured on discovery names only, tokenizer only, 2026-11-14: 2:1, 3:17, 4:22, 5:7, 6:1). No model is run by the generator |
| Pairing | entities are paired consecutively in generation order: pair `i` is entities `(2i, 2i+1)`. **No pair is redrawn or dropped afterwards** |
| Answer balancing | see §2.1 (deterministic; no rejection; no model quantity) |
| Primary order | a seeded coin per pair (from the split's own `random.Random(seed)` stream, drawn after names and answers) decides which member is A; the reverse order is secondary |
| Retention set RET | see §2.2 |
| Collateral sets | the existing 24 real facts and 8 neutral texts are reused unchanged (they are not entity-specific; their limits are the fixed `DESIGN.md` §7 gates) |

### 2.1 Answer balancing algorithm (fixed before generation)

Let `R = random.Random(seed)` for the split, and `ANS` the 12 answers in the fixed order of `build_tasks.py`.

- **CAL (8 entities, 12 answers): approximately balanced.** `p = R.sample(ANS, 12)`; entity `j` receives `p[j]` for `j = 0..7`. Each answer
  occurs **at most once**, so the two members of every pair differ.
- **CONF (24 entities): each of the 12 answers exactly twice.** `p = R.sample(ANS, 12)`; `k = R.randint(1, 11)`; pair `i` (`i = 0..11`) is
  `(p[i], p[(i + k) % 12])`. Every answer appears once as first member and once as second member (so exactly twice overall) and the two
  members differ because `k != 0 (mod 12)`.
- **RET (24 entities): each of the 12 answers exactly twice**, `p1 = R.sample(ANS, 12)`, `p2 = R.sample(ANS, 12)`, entity `j` gets
  `(p1 + p2)[j]`; no pair constraint (RET entities are not paired).
- No step looks at the model. No entity is accepted, rejected or redrawn because of how easy its answer is.

### 2.2 Retention set RET (fixed before generation)

For the distillation arm the retention set has **exactly 24 prompts**:

    RET = { x_A } ∪ { x_1, ..., x_23 }

where `x_A` is the **first patch's original training prompt** (`The capital of {A} is`), and `x_1..x_23` are the **training-template prompts
of the first 23 entities of the RET split in generation order**: the same 23 for every pair, every order and both arms that use them. This
keeps the 24-prompt budget of RETAIN-1 (one first-patch prompt plus 23 others). The 24th RET-split entity is **not** in RET; it is held
back as an unrelated leakage entity. Rules:

- RET never contains a held-out paraphrase, a real-fact prompt, a neutral text, any entity of CAL or CONF, or the second patch's prompt;
- the **rehearsal** arm uses only `x_A` (1 prompt) and the **new-task-only** and **composition** arms use none, so the arms do not have
  equal retention budgets; the stored retention information per arm is reported (R: 1 prompt, D: 24 prompts plus teacher logits);
- the teacher for D is the first-patch-only model W1; the teacher distributions are computed once per pair and stored.

### 2.3 Leakage entities (fixed before generation)

Distillation directly optimises stability on the 23 RET entities, so leakage measured **only** on those would flatter D. Leakage is
therefore reported on two disjoint sets of unrelated prompts:

- **uncovered unrelated set (the one the X gates use, identical for every arm):** the pair's partner, the 24th RET-split entity, and the other 22
  entities of the CONF split (CAL: the other 6 CAL entities) that belong to other pairs and are never patched in this pair's chain;
- **RET-covered set (descriptive only):** the 23 RET prompts; reported, never gated, flagged as optimised-for under D.

## 3. What is forbidden

- **No model quantity enters selection**: no base-model competence filter, no address cosine, no leakage or activation statistic.
  The generator runs no model. Any base-model measurement is made later by the experiment harness, recorded, and used for nothing in selection.
- The generator is **not changed after any model has been run on any of its outputs.** A defect found by the schema/disjointness
  checks *before* any model run may be fixed by a new committed generator version, regenerating from the same seeds, with both
  versions logged; after the first model run on a split, no regeneration of that split.
- No example from CONF is examined beyond the checks in §4 until the protocol is frozen.

## 4. Order of operations

1. Review and approve this plan and the data-related text of `PATCH-TRAIN-2.md`.
2. Commit the generator, its schema, its tests (using throw-away dummy seeds, **never** 20261121-23) and the real seeds file.
   Tests check determinism, disjointness, answer balance (§2.1), pair-answer inequality, the RET definition (§2.2) and tokenisation.
3. Generate **CAL and RET only**; commit them. Allowed checks: counts, disjointness, schema, token counts.
4. Run calibration on CAL/RET (`PATCH-TRAIN-2-CALIBRATION-PLAN.md`); review; freeze `PATCH-TRAIN-2.md`.
5. **Only after freeze**, generate CONF with the unchanged generator; commit it; check counts, disjointness and schema only; run.

## 5. Residual risks stated up front

- Name-neighbour similarity inside a split can still cause leakage (as in discovery); that is the quantity X measures, not a
  defect.
- The generator reuses the discovery syllable space, so a generated name could sit close to a discovery name; exact-match exclusion
  is fixed, near-match is recorded (normalised edit distance) and is not an exclusion.
- Same model, relation, answers and templates: results say nothing about other relations or models.
